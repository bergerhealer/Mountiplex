# Remapping Internals (Maintainers Only)

Audience: people changing Mountiplex itself. Users of the library do not need this page.
Terms are defined in [../glossary.md](../glossary.md).

Two different kinds of "remapping" exist and are easy to confuse:

| Kind | What it does | Where |
|---|---|---|
| **Resolver remapping** | Mountiplex's own translation of class, field and method names from the names written in templates and code to the names that exist in the environment | `reflection/resolver/`, `reflection/util/asm/javassist/` |
| **Class loader remapping** | An external bytecode-rewriting class loader (the one that loaded Mountiplex, for example on hybrid server software) that rewrites class, method and field names inside loaded bytecode | Outside the project; Mountiplex only has to cope with it via `MPLType` and `GeneratorClassLoader` |

## Class Loader Remapping and MPLType

`MPLType` (`reflection/util/asm/`; usage for generating classes is in [../class-generation.md](../class-generation.md)) provides the raw names and descriptors of classes, methods,
fields and constructors for all bytecode generation. It replaces the equivalent parts of ASM's
`Type` and direct calls such as `Class.getName()`.

Why: some environments (for example servers based on Forge, whose names differ entirely from the
ones used by the templates) install a custom class loader that loads Mountiplex and related classes
and automatically rewrites calls such as `Class.forName` and `Field.getName` inside the loaded bytecode,
so they return remapped names. That conflicts with Mountiplex's own Resolver remapping: names would be
translated twice or incorrectly, and generated bytecode needs the true JVM names. The global toggle
exists so Mountiplex can either bypass that rewriting or, where the environment's remapping must be
honoured, let it happen.

How it works:

- All lookups go through a `MPLTypeHelper` (interface with class name, method name,
  field name, declared method/field lookup and class-by-name methods).
- Two helpers exist:
  - **Remapping disabled** (the default): a helper class generated at runtime as raw bytecode with
    ASM and defined through `GeneratorClassLoader` with remapping not allowed. Because it is generated and
    defined through a path the external loader cannot intercept, its calls to `Class.getName()` and similar
    methods stay untouched.
  - **Remapping enabled**: `DefaultMPLTypeHelper`, plain Java calls that the external loader may rewrite.
- The helper is swapped with `MPLType.setRemappingEnabled(boolean)`. Callers should not use it
  directly; use `Resolver.setClassLoaderRemappingEnabled(boolean)`, which sets the Resolver flag and calls `MPLType`.
  `Resolver.isClassLoaderRemappingEnabled()` reads the flag.
  `GeneratorClassLoader.createClassFromBytecode(..., allowRemapping)` consults the same flag: with
  remapping disabled, or `allowRemapping` false, it uses the generated `defineClassFromBytecode` instead of the normal
  `defineClass`, so the loader cannot alter the bytecode.
- In BKCommonLib the flag is turned on during `postInit` by the Arclight and Magma server support
  classes, the environments where the class loader performs remapping that must be honoured.
  Everywhere else it stays off. Treat the exact intent of "enabled" as: the external loader is allowed to
  remap generated code and definitions.
- The same idea is applied to `GeneratorClassLoader` itself: `MPLGeneratorClassLoaderBuilder` generates its
  implementation as bytecode, and calls `defineClass` (JDK 8) or `MethodHandles.Lookup.defineClass` (JDK 9+)
  reflectively, so an eager environment cannot rewrite those calls either.

Other `MPLType` behaviour worth knowing:

- `getName(Method)` and `getName(Field)` additionally run the helper result through
  `Resolver.resolveCompiledMethodName` / `resolveCompiledFieldName`, so these return the
  name as compiled, mapped by the Resolver.
- `getClassByName` loads through the helper, then falls back to classes previously produced by
  `GeneratorClassLoader` (`findGeneratedClass`). It throws `LoaderClosedException` when a
  URL class loader's jar has been closed so that callers can discard that loader.
- `getDeclaredMethod`/`getDeclaredField` and the `tryGet...CheckSuperclasses` variants search through the helper too.
- The helper is static, global state; changing it affects all later generation.

**Rule for contributors:** code that generates bytecode or reads names from `Class`, `Method` or `Field`
for use in generated code must use `MPLType`, never `Class.getName()`,
`Type.getInternalName` or similar directly. Adding a new lookup means adding it to `MPLTypeHelper`
and to both helpers.

## Resolver Remapping and the Javassist Glue

[Javassist](https://www.javassist.org/) cannot remap names on its own. The `reflection/util/asm/javassist/`
package extends Javassist classes and overrides methods (some using reflection into package-private state) so that code in template method bodies
is compiled with names translated by the `Resolver`:

| Class | Role |
|---|---|
| `MPLCtNewMethod` | Replacement for Javassist's `CtNewMethod.make`; compiles method source using `MPLJavac`. |
| `MPLJavac` | Builds a Javassist `Javac` compiler with its code generator and symbol table swapped for the modified ones (constructed without calling constructors, fields set reflectively). Requires the class to belong to a `ResolvedClassPool`. |
| `MPLJvstCodeGen` | Replaces `JvstCodeGen`; installs `MPLJvstTypeChecker` and `MPLMemberResolver`. |
| `MPLJvstTypeChecker` | Avoids double-resolving class names when a method is called on a variable whose type is looked up. |
| `MPLMemberResolver` | Replaces `MemberResolver`; remaps field and method names with `Resolver.resolveFieldName` / `resolveMethodName` and class names for lookups. |

Related pieces outside that package:

- `ResolvedClassPool` (`reflection/resolver/`): a Javassist `ClassPool` that remaps class names
  through the `Resolver`. Pools are cached and reused: obtain with `create()` and close when done
  (try-with-resources). It also tracks imports and remapping rules from the `ClassResolver`.
  It can temporarily ignore the resolver (`ignoreResolver()` token) to look up already-resolved types and avoid
  resolve loops.
- `ClassBytecodeLoader` (`reflection/util/asm/`): provides the class data Javassist compiles against.
  Javassist works on bytecode, not Java types, so it needs `.class` data for every class referenced.
  This loader can instead produce a mock: an empty shim with only the signatures of the
  methods, fields and constructors of the loaded `Class`, built via reflection, with no implementation.
  This is needed for classes that have no `.class` file (for example classes generated at runtime), and for
  environments where the `.class` file in the jar conflicts with the `Class` that is actually loaded (for example
  because the server applies runtime patches or name translation). The mock describes what the loaded class really
  looks like, without ever parsing the possibly mismatched compiled file. When the `.class` file is trustworthy it is preferred.
- `ClassPathResolver.canLoadClassPath` (`reflection/resolver/`, aggregated by
  `Resolver.canLoadClassPath`, consulted by `ClassBytecodeLoader`): lets external projects (such as
  [BKCommonLib](https://github.com/bergerhealer/BKCommonLib), for its Arclight support) decide per class path whether
  the `.class` file may be read directly (default `true`) or whether a mock must be generated instead because the file is
  not compatible. Resolvers in a chain all must agree (`ChainResolver` combines them with AND).
- `MPL_NOREMAP$` prefix (`MPLMemberResolver.IGNORE_PREFIX`): names carrying this prefix are exempt from remapping
  and the prefix is stripped before compilation. Used by `MethodDeclaration`, `FieldDeclaration` and
  `MethodBodyBuilder` when emitting code that already uses the final name, to prevent double-renaming.
- `MethodBodyBuilder` and the declaration classes decide when generated source is emitted with remapped
  or exempt names.

Maintenance notes:

- This glue depends on Javassist internals (field and method names accessed reflectively in static
  initializers). Upgrading the Javassist version in `build.gradle.kts` requires re-checking these.
  Static initializer failures surface as errors when the class is first loaded.
- Class remapping is done by the `ClassPool`; member remapping by `MPLMemberResolver`. Keep each in its own layer to
  avoid renaming a name twice.
- Remapping can recurse (looking up a superclass's field triggers more lookups). The `ignoreResolver` tokens
  exist for this; use them when looking up already-resolved types.
